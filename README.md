# xuanyuan-kernel

Сборка ядра для Xiaomi 15 Ultra (`xuanyuan`, GKI `android15-6.6`).

Исходники ядра здесь **не хранятся**. В репозитории лежат только патчи, рецепт
сборки и закреплённые версии; само дерево GKI выкачивается из AOSP, а
KernelSU-Next и susFS — из своих апстримов. Собранные образы публикуются в
[releases](../../releases).

## Варианты

| вариант | что внутри |
|---|---|
| `vanilla` | чистый GKI, без рута |
| `ksunext` | KernelSU-Next |
| `ksunext-susfs` | KernelSU-Next + susFS |

Во все варианты входят три небольших апстримных патча WildKernels, отобранных
как безопасные для этого устройства (`patches/common/`). BBRv3 и NTSYNC оттуда
**исключены**: обе сборки с ними уходили в bootloop.

## Прошивка

Образ пишется в активный слот:

```bash
fastboot flash boot_a ksunext-susfs-boot.img
```

Узнать активный слот: `fastboot getvar current-slot`.

### Уровень патча в boot-образе — читать обязательно

Загрузчик берёт `BOOT_PATCHLEVEL` из AVB-свойства
`com.android.build.boot.security_patch` **внутри boot.img** и передаёт его в
TEE. Ключи keystore привязываются к этому значению, а KeyMint двигает его
**только вверх**.

Отсюда следствие, стоившее одному владельцу вечера:

> Прошивка boot-образа с уровнем **ниже** того, под которым выпущены ключи,
> делает их непригодными. `/data` перестаёт расшифровываться, TEE отвечает
> `INVALID_ARGUMENT (-38)`. Понижение необратимо — вернуть ключи на меньший
> уровень нельзя ничем, кроме сброса к заводским настройкам.

Практические следствия:

* Kleaf проставляет в собранный образ собственное значение, и оно бывает датой
  из будущего. Прошив такой образ, вы загоняете ключи в эту дату, после чего не
  подойдёт уже **ни один** нормальный образ. Поэтому значение задаётся явно
  через `BOOT_SECURITY_PATCH` в `config/versions.env`.
* Значение стоит держать равным тому, под которым ключи уже выпущены, и не
  повышать без необходимости: каждый шаг вверх отрезает все образы ниже.
* Перед прошивкой **любого** образа, включая чужие и стоковые:

  ```bash
  scripts/set-boot-patchlevel.sh boot.img            # показать
  scripts/set-boot-patchlevel.sh boot.img 2026-05-01 # изменить на месте
  ```

  Замена побайтовая, длина даты постоянна. Подпись AVB становится неверной, но
  при разблокированном загрузчике не проверяется.

## Обновление под новую прошивку

1. Достать параметры из стокового `boot.img` новой версии:

   ```bash
   scripts/stock-kernel-string.sh boot.img
   ```

   Скрипт печатает `GKI_COMMON_REF`, `KERNEL_BASE_VERSION`, строки для
   `uname -r` / `uname -v` и объявленный уровень патча.

2. Обновить `config/versions.env`.

3. Запустить workflow. Точные коммиты, из которых собран каждый вариант,
   попадают в `versions.lock.txt` рядом с образами.

## Локальная сборка

Нужен Linux, ~80 ГБ свободного места и много оперативной памяти.

```bash
./scripts/setup-source.sh                 # выкачать GKI (repo sync)
./scripts/prepare.sh ksunext-susfs        # патчи + KSU-Next + susFS
./scripts/build.sh   ksunext-susfs        # сборка, результат в dist/
```

## Структура

```
config/versions.env        закреплённые версии и параметры (перекрываются окружением)
config/fragments/          фрагменты defconfig для KSU и susFS
patches/common/            патчи, общие для всех вариантов
patches/device/            патчи под конкретное устройство
series/<вариант>           какие патчи в каком порядке идут в вариант
scripts/                   выкачивание, подготовка, сборка, работа с boot.img
.github/workflows/build.yml
```

Патчи применяются в порядке, заданном файлом `series/<вариант>`. Чтобы добавить
свой — положить `.patch` в `patches/` и вписать строку в нужные series.
