# xuanyuan-kernel

Сборка ядра для Xiaomi 15 Ultra (`xuanyuan`, GKI `android15-6.6`).

Исходники ядра здесь **не хранятся**. В репозитории лежат только патчи, рецепт
сборки и закреплённые версии; само дерево GKI выкачивается из AOSP, а
KernelSU-Next и susFS — из своих апстримов. Собранные образы публикуются в
[releases](../../releases).

## Варианты

| вариант | что внутри |
|---|---|
| `vanilla` | чистый GKI, без рута |
| `ksunext` | KernelSU-Next |
| `ksunext-susfs` | KernelSU-Next + susFS |

Во все варианты входят три небольших апстримных патча WildKernels, отобранных
как безопасные для этого устройства (`patches/common/`). BBRv3 и NTSYNC оттуда
**исключены**: обе сборки с ними уходили в bootloop.

## Прошивка

Релиз содержит **ядро и модули, а не готовый к прошивке образ**. Так вышло не
из лени: Kleaf собирает `boot.img` по разметке GKI — 64 МиБ, — тогда как раздел
`boot` у `xuanyuan` занимает 96 МиБ, и прошивка образа GKI приводит к bootloop.

Рабочий образ получается заменой ядра внутри **стокового** `boot.img`: заголовок,
размер раздела и структура AVB остаются заводскими. Стоковый образ — часть
прошивки Xiaomi, распространять его здесь нельзя, поэтому шаг выполняется у вас.

```bash
# стоковый boot.img берётся из fastboot-ROM вашей версии: images/boot.img
scripts/repack-boot.sh стоковый-boot.img Image готовый-boot.img

fastboot getvar current-slot        # узнать активный слот
fastboot flash boot_a готовый-boot.img
```

Скрипт не просто подменяет ядро: вслед за изменившимся размером он двигает
блок vbmeta и правит `original_image_size` с `vbmeta_offset` в AVBf-footer в
конце раздела. Без этого загрузчик читал бы свойства не оттуда и не увидел бы
`boot.security_patch`. Результат проверяется — размер, заголовок, побайтовое
совпадение ядра, доступность vbmeta и наличие свойства.

Подписи AVB после замены ядра недействительны. При разблокированном загрузчике
они не проверяются; на заблокированном такой образ не загрузится, и это
ожидаемо.

### Уровень патча в boot-образе — читать обязательно

Загрузчик берёт `BOOT_PATCHLEVEL` из AVB-свойства
`com.android.build.boot.security_patch` **внутри boot.img** и передаёт его в
TEE. Ключи keystore привязываются к этому значению, а KeyMint двигает его
**только вверх**.

> **Правило: в образе должно стоять ровно то, что объявляет стоковый `boot.img`
> вашей прошивки.** Ни ниже, ни выше.

Что бывает при отклонении в каждую сторону:

* **Ниже** — ключи, выпущенные под текущим уровнем, становятся непригодны.
  `/data` перестаёт расшифровываться, TEE отвечает `INVALID_ARGUMENT (-38)`,
  телефон грузится, принимает ПИН, но приложения не запускаются.
* **Выше** — хуже, потому что ломается не сразу. Образ прошьётся и заработает,
  но ключи привяжутся к завышенной дате, и после этого **любой** стоковый образ
  станет для них понижением. Перестанут работать и OTA (она кладёт в `boot`
  сток), и откат на другую версию прошивки. Понижение необратимо: вернуть ключи
  на меньший уровень нельзя ничем, кроме сброса к заводским настройкам.

Поэтому завышать дату «на всякий случай» нельзя — это не запас прочности, а
замок без ключа. Kleaf, к слову, сам проставляет в собранный образ произвольное
значение, и там встречаются даты вроде `2099-12-31`; один такой образ отрезает
вообще всё. Именно ради этого `BOOT_SECURITY_PATCH` задаётся явно.

Узнать правильное значение и сверить готовый образ:

```bash
scripts/stock-kernel-string.sh стоковый-boot.img   # что объявляет сток
scripts/set-boot-patchlevel.sh boot.img            # что объявляет наш образ
scripts/set-boot-patchlevel.sh boot.img 2026-02-01 # поправить на месте
```

Делать это стоит перед прошивкой **любого** образа, включая чужие сборки:
замена побайтовая, длина даты постоянна, подпись AVB при этом становится
неверной, но при разблокированном загрузчике не проверяется.

Если ключи вашего устройства уже привязаны к завышенному уровню — например,
после чужой сборки с такой датой, — то придётся и дальше собирать с ним же.
Проверить, к чему привязаны ключи, можно по дате в уже работающем образе.

## Обновление под новую прошивку

1. Достать параметры из стокового `boot.img` новой версии:

   ```bash
   scripts/stock-kernel-string.sh boot.img
   ```

   Скрипт печатает `GKI_COMMON_REF`, `KERNEL_BASE_VERSION`, строки для
   `uname -r` / `uname -v` и объявленный уровень патча.

2. Обновить `config/versions.env`.

3. Запустить workflow. Точные коммиты, из которых собран каждый вариант,
   попадают в `versions.lock.txt` рядом с образами.

## Локальная сборка

Нужен Linux, ~80 ГБ свободного места и много оперативной памяти.

```bash
./scripts/setup-source.sh                 # выкачать GKI (repo sync)
./scripts/prepare.sh ksunext-susfs        # патчи + KSU-Next + susFS
./scripts/build.sh   ksunext-susfs        # сборка, результат в dist/
```

## Структура

```
config/versions.env        закреплённые версии и параметры (перекрываются окружением)
config/fragments/          фрагменты defconfig для KSU и susFS
patches/common/            патчи, общие для всех вариантов
patches/device/            патчи под конкретное устройство
series/<вариант>           какие патчи в каком порядке идут в вариант
scripts/                   выкачивание, подготовка, сборка, работа с boot.img
.github/workflows/build.yml
```

Патчи применяются в порядке, заданном файлом `series/<вариант>`. Чтобы добавить
свой — положить `.patch` в `patches/` и вписать строку в нужные series.
